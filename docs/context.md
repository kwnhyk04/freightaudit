## Overview and Objectives

AI-native portfolio project showing document extraction plus deterministic reconciliation for freight invoice audit (logistics / accounts payable domain).

## Scope and Requirements

- Upload single invoices or batches of up to 500 PDFs (digital and scanned).
- LLM extraction of header fields and line items, with validation, one repair attempt, and escalation to the fallback model.
- Deterministic reconciliation against versioned rate cards and shipments synced from a mock TMS.
- Review UI for discrepancies.
- Must demonstrate: backpressure, retries, pagination, partial failures, schema migrations.

Targets (design goals, not yet measured):

## Architecture and System Design

Workspaces exist as skeletons (step 1). Behavior below is planned unless listed under Implemented Functionality.

1. `apps/api`: Fastify REST + GraphQL. Stores PDFs in MinIO by content hash, writes invoice rows, enqueues `extract`. Returns 503 with Retry-After while more than `EXTRACT_HIGH_WATER` (5,000) extract jobs wait.
2. `apps/worker`: BullMQ queues `extract`, `reconcile`, `tms-sync`, each with a `<name>-dlq` dead-letter queue.
3. `apps/mock-tms`: fake TMS with cursor pagination, 10 req/s rate limit, fault injection.
4. `apps/web`: Next.js review UI over GraphQL.
5. `packages/domain`: money, rate-card math, reconciliation. Pure functions.
6. `packages/llm` (provider layer, error taxonomy, PDF handling, AI limits), `packages/pipeline` (queues and job options, dead letters and replay, PDF object store; shared by api and worker), `packages/db`, `packages/contracts`, `packages/telemetry`, `evals/`.

Tooling: `packages/config` holds the shared tsconfig, ESLint and Jest presets plus the runtime env loader (`@freightaudit/config/env`). `packages/telemetry` holds the shared Fastify logging options and readiness checks. Packages build to `dist/` with `tsc`; apps run TypeScript directly in dev through Node type stripping. Local infrastructure lives in `infra/docker-compose.yml`; `infra/docker-compose.prod.yml` overrides it for the backend on the PC.

## Invoice Lifecycle

One status set in Postgres (`invoice_status`), REST (`InvoiceStatus`, lowercase) and GraphQL (`InvoiceStatus`, uppercase): received, extracting, extracted, reconciling, reconciled, needs_review, approved, failed (user decision, 2026-10-14). An invoice starts as received when the api stores a new PDF. The table lists every allowed move; the `check_invoice_transition` trigger (migration 0006, replaced in 0007) rejects any other update of `status`, whichever code writes it, and rejects approval while any of the invoice's discrepancies is open. Repeating the current status is allowed.

Findings do not change the status (user decision, 2026-10-14): an invoice with findings ends as reconciled, and each finding waits as an open discrepancy in the review queue (open discrepancies across invoices, GraphQL `discrepancies(status: OPEN)`). needs_review is reserved for extractions that could not be trusted; today the reconcile job sets it when the extracted carrier or PRO number matches no shipment.

| From | To | When |
| --- | --- | --- |
| received | extracting | The extract worker starts the job. |
| extracting | extracted | Extraction passes validation, after at most one repair. |
| extracting | failed | Extraction used up its retries; the job moves to `dead_letters`, whose error the api shows as the invoice's `failure_reason`. |
| extracted | reconciling | The reconcile worker starts the job. |
| reconciling | reconciled | The shipment matched, and every line was checked against the rate card version in force on the ship date; each finding is saved as an open discrepancy. |
| reconciling | needs_review | The extracted carrier or PRO number matches no shipment, so the extraction cannot be trusted. |
| reconciling | failed | Reconciliation used up its retries or met data it cannot price (no version in force, a version without linehaul terms, a shipment without miles); the job moves to `dead_letters`, and the worker's dead-letter handler marks the invoice failed with that error as its `failure_reason`. |
| reconciled | approved | `approveInvoice`, once every discrepancy is confirmed or dismissed (the trigger enforces it). |
| needs_review | approved | `approveInvoice`, once a reviewer has checked the document. |
| failed | received | Replay of an `extract` dead letter; it closes the dead letter, which clears `failure_reason`. |
| failed | extracted | Replay of a `reconcile` dead letter, once the data is fixed; the job then reconciles the invoice. |

`approved` is final. A retried job keeps the current status, because jobs are idempotent (job id = content hash). Never sort by status: Postgres orders the enum `received, extracting, extracted, reconciling, needs_review, reconciled, approved, failed`, since values added by 0005 cannot move existing ones.

- Monorepo: root scripts `dev`, `build`, `test`, `lint`, `typecheck`, `db:migrate`, `db:seed`, `db:reset`, `fixtures`, `codegen`, `eval` run through Turborepo; `db:migrate`, `db:seed` and `fixtures` pass their arguments through (`turbo run <task> --`). `test:int` builds the packages through Turborepo, then runs the root Jest config.
- Database (`packages/db`): plain SQL migrations `0001_initial` (tenants, carriers, flat rate_cards, shipments, invoices, invoice_lines, discrepancies, idempotency_keys, dead_letters, tms_sync_state), then the rate card versioning series `0002` expand, `0003a` contract, `0003b` concurrent indexes and `0004` drop of `rate_cards.carrier_id`, then `0005`, which adds `reconciling` and `approved` to `invoice_status`, `0006` (`extractions`, `invoices.parent_invoice_id`, the status-transition trigger), `0007` (linehaul terms: `rate_card_versions.minimum_cents` and `fuel_bp`, the `rate_card_bands` table, `shipments.miles`, and approval only once no discrepancy is open) and `0008` (a concurrent index on `invoices.shipment_id`); `docs/migrations.md` explains each step. A version's `rate_cards` rows are its flat accessorial rates; its bands, minimum and fuel percentage price the linehaul and fuel surcharge. Ids default to `uuidv7()`, money is `bigint` cents, a trigger maintains `updated_at`, and list tables have `(tenant_id, created_at DESC, id DESC)` keyset indexes. `rate_card_versions` has an exclusion constraint against overlapping `effective` ranges per carrier, and every invoice line references the version that priced it. `src/migrate.ts` applies the files (advisory lock, `lock_timeout` 5 s, no-transaction files, `--to`); `src/schema.ts` is the Drizzle query mirror of the final state.
- Seed (`pnpm db:seed --scale=small|large`): deterministic (`faker.seed(42)`) data for an empty, migrated database, in one transaction; two small seeds give identical rows. Small is 1 tenant, 6 fictional carriers, 5,000 shipments and 500 invoices (1,268 lines, 454 extractions, 111 discrepancies of which 79 open, about 1 s); large is 50,000 shipments and 20,000 invoices (51,065 lines, 18,232 extractions, 4,842 discrepancies, about 17 s). Each carrier gets two rate card versions, with a rate increase on 2026-01-01: three graduated per-mile bands (from miles 0, 250 and 1,000), a minimum, a fuel percentage and four accessorials; shipments get 25 to 2,500 miles. Lines bill what the version in force on the ship date contracts (linehaul and fuel through `rateShipment`), plus one planted overcharge (rate mismatch, uncontracted or duplicate charge) on half of the extracted, reconciling and reconciled invoices and 15 % of the approved ones. Invoices cover all 8 statuses and follow the lifecycle: every invoice past extraction has an `extractions` row in the model's output shape; reconciled and approved ones have lines and a shipment, with their findings open on reconciled invoices and decided on approved ones; extracted and reconciling ones wait for the reconcile job, so their planted overcharges exist only in the ground truth; needs_review ones carry a PRO number with its last digit misread, which matches no shipment. `seed()` returns its ground truth (`buildSeed` builds it in memory): for each invoice a reconciler can check, every line's contracted and billed cents and every planted overcharge with its expected cents, billed cents and explanation.
- Reset (`pnpm db:reset`, dev only, `packages/pipeline/scripts/reset.ts`): obliterates this deployment's BullMQ queues and dead-letter queues with BullMQ's `obliterate` (jobs and their ids, so a PDF uploaded before the reset is extracted again), refusing while a job runs and unless Redis is on localhost or 127.0.0.1; then, through `packages/db/scripts/reset.ts`, it drops schema `public` (every app table, type, function and its data) and recreates it as a new database has it, migrates from empty and seeds `--scale=small` (about 3 s). It refuses before connecting unless the host pg will connect to (a `host` parameter in the URL included) is `localhost` or `127.0.0.1` and `NODE_ENV` is not `production`; the Turborepo task passes `NODE_ENV` through, since strict env mode would drop it. Both hosts and `NODE_ENV` are checked before anything is deleted. It waits at most 5 s for database locks, so a running api or worker makes it fail instead of hang. Stored PDFs and the AI counters in Redis are untouched.
- Backfill (`pnpm --filter @freightaudit/db backfill:rate-card-versions`): between 0002 and 0003a it creates version 1 per carrier from the flat rates and fills `rate_card_version_id` in batches of 2,000 with `lock_timeout` 3 s, retries, JSON progress logs and an exit code of 1 while rows remain.

- Contracts (spec-first, `packages/contracts`): `openapi.yaml` (OpenAPI 3.1) defines `POST /v1/invoices` (multipart PDF, required `Idempotency-Key`, 202 new or 200 existing by content hash), `POST /v1/invoice-batches` (up to 500 files, per-file `accepted | duplicate | rejected` results), `GET /v1/invoices` and `GET /v1/discrepancies` (`limit` 1 to 100, default 25, opaque `cursor`, `{items, next_cursor}`), `GET /v1/invoices/{id}`, `POST /v1/dead-letters/{id}/replay`, `/healthz` and `/readyz`. An `ApiKey` scheme (`X-API-Key` header) applies to every operation except the two probes; the secured operations document 401 and 403. Errors are RFC 9457 Problem Details; 429 documents `RateLimit-Limit`, `RateLimit-Remaining` and `Retry-After`, and 503 documents `Retry-After`. `schema.graphql` defines the review UI types (Invoice, LineItem, Shipment, RateCardVersion, Discrepancy), Relay connections for invoices and discrepancies, and the `resolveDiscrepancy` and `approveInvoice` mutations; `operations/` holds the UI operations.
- Codegen: openapi-typescript types plus an openapi-fetch client (`createApiClient`), graphql-codegen resolver types (exported from `@freightaudit/contracts`) and client-preset typed documents (`@freightaudit/contracts/graphql`). `pnpm contracts:check` fails on stale generated code; `pnpm contracts:breaking` runs oasdiff against `origin/main`.
- api: fastify-openapi-glue registers every REST route from `openapi.yaml` and validates requests against it; each multipart file is read (at most 10 MiB), checked (`%PDF-` magic, readable by pdf-lib, at most 20 pages; else 413 or 415, per file in a batch), stored in MinIO under its SHA-256 and validated as that digest. Handlers use Postgres: an upload inserts the invoice (unique per tenant and hash), records the Idempotency-Key and adds an `extract` job whose id is the hash; lists use keyset cursors (`created_at` to the microsecond plus `id`, base64url JSON); replay calls `replayDeadLetter`. Before the body is read, an `onRequest` chain checks the API key, then sheds uploads with 503 and `Retry-After: 30` while the extract backlog (waiting plus delayed jobs, since the budget guard parks jobs in delayed) is above `EXTRACT_HIGH_WATER`, then rate-limits per key digest in Redis (@fastify/rate-limit, draft RateLimit headers): 60 requests a minute, and a separate 10 a minute for the two upload routes. `requestTimeout` is 30 s. GraphQL Yoga serves the full schema at `/graphql`, but only the `health` query has a resolver. `openapi.contract.test.ts` (the contract project) calls every REST operation through the typed client against a throwaway database and validates each response against the spec, including 401 for every secured operation.
- Worker (`apps/worker`): `extract` (concurrency 8), `reconcile` (8) and `tms-sync` (1) workers share one Redis connection, a 60 s lock (`JOB_LOCK_MS`), stalled checks every half lock, `maxStalledCount` 1 and the `jittered` backoff (exponential from 2 s, capped at 60 s, full jitter, never below an error's Retry-After); jobs have 5 attempts. An extract job loads the invoice, delays itself with `moveToDelayed` until the next UTC midnight once the day's token budget is spent (5 minutes while `AI_ENABLED=false`), moves it to extracting, reads the PDF from MinIO, calls the model through the token bucket, validates with one repair, then saves one `extractions` row and the header fields in one transaction and queues `reconcile`. Rerunning it at any point writes nothing twice (status guards, unique `invoice_id`). A PDF holding several invoices is split by `first_page` into per-invoice PDFs and invoice rows (`parent_invoice_id`); a FlowProducer adds a `collect` parent with one child extract job per part (`ignoreDependencyOnFailure`), and the parent records each part's outcome in the upload's extraction row and marks it extracted. A reconcile job commits the move to reconciling on its own, then in one transaction locks the invoice row, matches the shipment by carrier and PRO number (locked too, so reconciles of one shipment run one at a time), loads the carrier's rate card versions (the domain picks the one in force on the ship date), its bands and accessorials, and the charge codes on other invoices already reconciled against the shipment, calls `reconcileInvoice`, writes the invoice lines (numbered by position, each with the version that priced it) and one discrepancy per finding (expected and billed cents, the explanation, the line and shipment), and sets reconciled with the shipment link. A carrier or PRO number that matches no shipment sets needs_review and writes nothing else; no version in force, a version without bands, minimum or fuel percentage, a shipment without miles, or a domain `RangeError` is permanent and dead-letters the job. A rerun or a second concurrent run waits on the invoice lock, finds the invoice reconciled and writes nothing. `tms-sync` runs every 5 minutes (one job scheduler), pages mock-tms from the saved cursor, upserts carriers and shipments (with miles) and saves the cursor in the same transaction per page, and retries a page in place on any transient failure (429, 5xx, timeouts, dropped connections) up to 10 times with the jittered backoff and a Retry-After floor; after that the attempt fails and the next resumes from the saved cursor. SIGTERM closes the workers after their running jobs.
- Error taxonomy (`packages/llm`): TransientError (timeouts, 408/425/429/5xx, dropped connections; carries Retry-After) is retried; PermanentError (unreadable or empty PDF, more than 20 pages, missing PDF, provider 4xx, output still invalid after the repair) becomes BullMQ `UnrecoverableError`. Validation messages name fields, never document values.
- Dead letters (`packages/pipeline`): one `failed` handler per worker; on a final failure it inserts a `dead_letters` row and marks the invoice failed, then copies the job to `<queue>-dlq`, all idempotent. The copy comes last and marks a finished move: every worker sweeps its queues' failed sets at start and every 5 minutes and redoes moves without a copy (a handler that failed, or a worker that died first). A failed query is rethrown as `database query failed: <code>`, because drizzle puts every bound value, extracted line items included, in its message. `POST /v1/dead-letters/{id}/replay` re-adds the job first (same id, the DLQ copy's name and data), then marks the row replayed and resets the invoice (extract to received, reconcile to extracted); a worker that still sees failed retries until that commits.
- AI limits: a Lua token bucket in Redis (`LLM_TOKENS_PER_MINUTE`, shared by all workers, estimate 5,200 tokens per page, trued up after each call), and per-UTC-day counters of calls and tokens checked against `DAILY_AI_TOKEN_BUDGET`. `AI_ENABLED=false` (the default) means no provider is built and extract jobs wait. `createLimits` takes an optional clock for tests; without one the bucket runs on the Redis clock and waits in real time. The provider is Gemini `generateContent` over `fetch` with the PDF inline and the key in a header.
- mock-tms: 1,000 generated shipments (`TMS-000001` on, each with miles), `GET /shipments?after=<cursor>&limit=<1-100>` returning `{ items, next_cursor, has_more }`, 10 requests per second (429 with `Retry-After: 1`), and `FAULT_RATE` / `LATENCY_MS` fault injection.
- GraphQL schema and operations pass graphql-eslint (schema-recommended, schema-relay, operations-recommended); `strict-id-in-types` exempts only `PageInfo` and `*Connection`/`*Edge` types.
- Domain math (`packages/domain`, money as bigint cents): `divRound` rounds halves away from zero; `percentOf` takes basis points (10,000 is 100 %) to the nearest cent; `rateShipment` prices one shipment from a rate card of graduated per-mile bands (each whole mile at its band's rate), a minimum linehaul and a fuel surcharge in basis points of the linehaul after the minimum, rounding only the fuel; `linesMatchTotal` checks that lines add up to the total. `reconcileInvoice` picks the version in force on the ship date (`versionInForce`: half-open UTC days, a null bound open on that side, overlaps rejected) and checks every billed line: a charge code billed before on this invoice or, through `billedBefore`, on an earlier invoice for the shipment is a `duplicate_charge`; a code the version does not contract is an `uncontracted_charge`; more than the linehaul, fuel surcharge or accessorial rate is a `rate_mismatch`. Only overcharges count, at most one per line, each with a `formatUsd` explanation. Findings do not decide the invoice status; the reconcile job applies the rules.
- `packages/domain` ESLint config allows relative imports only and bans dynamic `import()`; `purity.test.ts` checks it.
- Infra: Postgres, Redis, MinIO, OpenTelemetry Collector, Jaeger, Prometheus, Grafana and Toxiproxy with pinned images and healthchecks. The collector sends traces to Jaeger and exposes metrics that Prometheus scrapes; Grafana provisions both datasources; Toxiproxy proxies Postgres, Redis and the host mock-tms. The default `up` starts Postgres, Redis, MinIO and Toxiproxy.
- Production override (`infra/docker-compose.prod.yml`): no host ports for Postgres, Redis and MinIO, `restart: unless-stopped` and memory limits on every service, Redis capped at 200 MB with `noeviction`, Toxiproxy only with `--profile chaos`.

- All targets are design goals and have not been measured.
- `eval` is a no-op until step 6.
- Rate card versions written before 0007 have no bands, minimum or fuel percentage, and shipments synced before it have no miles until the TMS sync reads them again (clear its cursor, see `docs/migrations.md`); reconciling against them dead-letters the job until the data is entered (then replay it).
- A needs_review invoice has no way back to reconciliation yet: correcting an extraction belongs to the review UI (step 9). Its lines exist only in its extraction row, since lines are written once a version prices them.
- Duplicates across invoices compare against invoices already reconciled for the shipment, so of two invoices billing one charge, the one reconciled second carries the finding, whichever arrived first.
- Upload invoices that were split stay extracted with no lines of their own.- One tenant per deployment (`TENANT_ID`); API keys do not carry a tenant yet, and job ids are content hashes without the tenant.
- The Gemini provider is tested against a local fake only; no real key has been used yet. The Groq text path and the fallback model are not built.
- A split part whose bytes match an earlier upload reuses that invoice and job id; BullMQ then makes the old job a child of the split.
- Provider 401, 403 and 404 (bad key, retired model) are permanent, so every extract job dead-letters until the setting is fixed; replay them afterwards. A circuit breaker that pauses the queue instead is planned for step 6.
- `pnpm test:int` needs Docker and the Playwright Chromium (`pnpm --filter @freightaudit/evals exec playwright install --only-shell chromium`). `db:seed` refuses a database that already has data; `pnpm db:reset` empties and reseeds a local dev database.
- The Toxiproxy test reaches its fake TMS on the host as `host.docker.internal`. Docker Desktop forwards that to the host's loopback; on a Linux Docker engine `host-gateway` reaches only non-loopback addresses, so the fake TMS, bound to 127.0.0.1, is unreachable there (step 7 must solve this for CI).
- A test run killed before its teardown leaves its containers running until the next `pnpm test:int` removes them.
- The migration runner records names only, so an edited applied migration goes unnoticed.
- `backfill-rate-card-versions.ts` only works between 0002 and 0004; after 0004 `rate_cards.carrier_id` no longer exists.
- Fixture bytes repeat only on the same machine and Chromium build; other fonts or browser versions render differently. Fixture invoices are single-page, and their ground truth holds only for a database seeded with `--scale=small`.
- oasdiff reports the two new `InvoiceStatus` values as breaking (`response-property-enum-value-added`, ERR) against a base without them. `contracts:breaking` cannot run yet (no `origin/main`); once this spec is on main, later diffs start from it.
- 403 is documented but no key has restricted permissions. A request's 30 s `requestTimeout` covers receiving it, not the handler's work.
- GraphQL resolvers exist only for `health`; the `Cents` scalar has no runtime implementation yet.
- `contracts:breaking` fails until the repository has an `origin/main` remote branch (none is configured yet).
- Readiness proves TCP reachability only, not credentials; it switches to queries on the real clients when steps 3 and 4 add them.
- The web port is fixed at 3000 unless `--port` or `PORT` is passed to its dev script; Next.js does not read the root `.env`, and its own logs are not JSON.
- The production override still uses the dev-only Postgres and MinIO credentials from the base file.
- mock-tms serves a fixed set of shipments; new ones never appear, so later syncs read one empty page. `infra/toxiproxy.json` proxies mock-tms on port 4010 regardless of `MOCK_TMS_PORT`.
- MinIO runs the community fork image `pgsty/minio` because upstream images were withdrawn.
