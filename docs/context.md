## Overview and Objectives

AI-native portfolio project showing document extraction plus deterministic reconciliation for freight invoice audit (logistics / accounts payable domain).

## Scope and Requirements

- Upload single invoices or batches of up to 500 PDFs (digital and scanned).
- LLM extraction of header fields and line items, with validation, one repair attempt, and escalation to the fallback model.
- Deterministic reconciliation against versioned rate cards and shipments synced from a mock TMS.
- Review UI for discrepancies.
- Must demonstrate: backpressure, retries, pagination, partial failures, schema migrations.

## Architecture and System Design

Workspaces exist as skeletons (step 1). Behavior below is planned unless listed under Implemented Functionality.

1. `apps/api`: Fastify REST + GraphQL. Stores PDFs in MinIO by content hash, writes invoice rows, enqueues `extract`. Returns 503 with Retry-After while more than `EXTRACT_HIGH_WATER` (5,000) extract jobs wait.
2. `apps/worker`: BullMQ queues `extract`, `reconcile`, `tms-sync`, each with a `<name>-dlq` dead-letter queue.
3. `apps/mock-tms`: fake TMS with cursor pagination, 10 req/s rate limit, fault injection.
4. `apps/web`: Next.js review UI, a backend for frontend: its server calls the api's GraphQL and REST with a server-only key; the browser never calls the api.
5. `packages/domain`: money, rate-card math, reconciliation. Pure functions.
6. `packages/llm` (provider layer, error taxonomy, PDF handling, AI limits), `packages/pipeline` (queues and job options, dead letters and replay, PDF object store; shared by api and worker), `packages/db`, `packages/contracts`, `packages/telemetry`, `evals/`.

Tooling: `packages/config` holds the shared tsconfig, ESLint and Jest presets plus the runtime env loader (`@freightaudit/config/env`). `packages/telemetry` holds the shared Fastify logging options and readiness checks, every metric instrument, and `./sdk`, which starts OpenTelemetry. Packages build to `dist/` with `tsc`; apps run TypeScript directly in dev through Node type stripping. Local infrastructure lives in `infra/docker-compose.yml`; `infra/docker-compose.prod.yml` turns it into the public demo's own project, `freightaudit-prod`.

## Invoice Lifecycle

One status set in Postgres (`invoice_status`), REST (`InvoiceStatus`, lowercase) and GraphQL (`InvoiceStatus`, uppercase): received, extracting, extracted, reconciling, reconciled, needs_review, approved, rejected, failed (user decisions, 2026-10-14; rejected 2026-10-16). An invoice starts as received when the api stores a new PDF. The table lists every allowed move; the `check_invoice_transition` trigger (migration 0006, replaced in 0007 and 0013) rejects any other update of `status`, whichever code writes it, and rejects approval while any of the invoice's discrepancies is open. Repeating the current status is allowed. Since 0013 every status change is kept in `audit_events`: a trigger writes the pipeline's moves, and a reviewer action writes its own row (who, why, which fields) in the same transaction.

Findings do not change the status (user decision, 2026-10-14): an invoice with findings ends as reconciled, and each finding waits as an open discrepancy in the review queue (open discrepancies across invoices, GraphQL `discrepancies(status: OPEN)`). needs_review is reserved for extractions that could not be trusted: the extract job sets it when the model's output stays invalid after one repair and one pass on the fallback model, or when a scan with more page images than the fallback takes would need the fallback, and the reconcile job when the extracted carrier or PRO number matches no shipment.

| From | To | When |
| --- | --- | --- |
| received | extracting | The extract worker starts the job. |
| extracting | extracted | Extraction passes validation on the first pass, after one repair, or on the fallback model. |
| extracting | needs_review | The output stayed invalid after one repair and one pass on the fallback model (0009), or a scan with more page images than the fallback takes needed the fallback (problem `fallback_page_cap`); the extraction row keeps the problems and the output for a reviewer. |
| extracting | failed | Extraction used up its retries; the job moves to `dead_letters`, whose error the api shows as the invoice's `failure_reason`. |
| extracted | reconciling | The reconcile worker starts the job. |
| reconciling | reconciled | The shipment matched, and every line was checked against the rate card version in force on the ship date; each finding is saved as an open discrepancy. |
| reconciling | needs_review | The extracted carrier or PRO number matches no shipment, so the extraction cannot be trusted. |
| reconciling | failed | Reconciliation used up its retries or met data it cannot price (no version in force, a version without linehaul terms, a shipment without miles); the job moves to `dead_letters`, and the worker's dead-letter handler marks the invoice failed with that error as its `failure_reason`. |
| reconciled | approved | `approveInvoice`, once every discrepancy is confirmed or dismissed (the trigger enforces it). |
| needs_review | approved | `approveInvoice`, once a reviewer has checked the document. |
| needs_review | extracted | `correctInvoice`: a reviewer corrects the carrier or PRO number of an invoice whose reading matched no shipment (`no_shipment_match`); the reconcile job is queued again and matches with the corrected values (0013). |
| needs_review | rejected | `rejectInvoice` with a reason of 1 to 1,000 characters (0013). |
| failed | received | Replay of an `extract` dead letter; it closes the dead letter, which clears `failure_reason`. |
| failed | extracted | Replay of a `reconcile` dead letter, once the data is fixed; the job then reconciles the invoice. |

`approved` and `rejected` are final. A retried job keeps the current status, because jobs are idempotent (job id = content hash). Never sort by status: Postgres orders the enum `received, extracting, extracted, reconciling, needs_review, reconciled, approved, rejected, failed`, since values added later cannot move existing ones.

A version's `rate_cards` rows are its flat accessorial rates; its bands, minimum and fuel percentage price the linehaul and fuel surcharge. Ids default to `uuidv7()`, money is `bigint` cents, a trigger maintains `updated_at`, and list tables have `(tenant_id, created_at DESC, id DESC)` keyset indexes. `rate_card_versions` has an exclusion constraint against overlapping `effective` ranges per carrier, and every invoice line references the version that priced it. `src/migrate.ts` applies the files (advisory lock, `lock_timeout` 5 s, no-transaction files, `--to`); `src/schema.ts` is the Drizzle query mirror of the final state.
- Seed (`pnpm db:seed --scale=small|large`): deterministic (`faker.seed(42)`) data for an empty, migrated database, in one transaction; two small seeds give identical rows. Small is 1 tenant, 6 fictional carriers, 5,000 shipments and 500 invoices (1,268 lines, 454 extractions, 111 discrepancies of which 79 open, about 1 s); large is 50,000 shipments and 20,000 invoices (51,065 lines, 18,232 extractions, 4,842 discrepancies, about 17 s). Each carrier gets two rate card versions, with a rate increase on 2026-01-01: three graduated per-mile bands (from miles 0, 250 and 1,000), a minimum, a fuel percentage and four accessorials; shipments get 25 to 2,500 miles. Lines bill what the version in force on the ship date contracts (linehaul and fuel through `rateShipment`), plus one planted overcharge (rate mismatch, uncontracted or duplicate charge) on half of the extracted, reconciling and reconciled invoices and 15 % of the approved ones. Invoices cover all 8 statuses and follow the lifecycle: every invoice past extraction has an `extractions` row in the model's output shape; reconciled and approved ones have lines and a shipment, with their findings open on reconciled invoices and decided on approved ones; extracted and reconciling ones wait for the reconcile job, so their planted overcharges exist only in the ground truth; needs_review ones carry a PRO number with its last digit misread, which matches no shipment. `seed()` returns its ground truth (`buildSeed` builds it in memory): for each invoice a reconciler can check, every line's contracted and billed cents and every planted overcharge with its expected cents, billed cents and explanation.
- Reset (`pnpm db:reset`, dev only, `packages/pipeline/scripts/reset.ts`): obliterates this deployment's BullMQ queues and dead-letter queues with BullMQ's `obliterate` (jobs and their ids, so a PDF uploaded before the reset is extracted again), refusing while a job runs and unless Redis is on localhost or 127.0.0.1; then, through `packages/db/scripts/reset.ts`, it drops schema `public` (every app table, type, function and its data) and recreates it as a new database has it, migrates from empty and seeds `--scale=small` (about 3 s). Both hosts and `NODE_ENV` are checked before anything is deleted. It waits at most 5 s for database locks, so a running api or worker makes it fail instead of hang. - Worker (`apps/worker`): `extract` (concurrency 8; on branch `c2b-c3`, `EXTRACT_CONCURRENCY`, 1 to 8, default 8, and 1 on the demo), `reconcile` (8) and `tms-sync` (1) workers share one Redis connection, a 60 s lock (`JOB_LOCK_MS`), stalled checks every half lock, `maxStalledCount` 1 and the `jittered` backoff (exponential from 2 s, capped at 60 s, full jitter, never below an error's Retry-After); jobs have 5 attempts. An extract job loads the invoice, delays itself with `moveToDelayed` until the next UTC midnight once the day's token budget is spent (5 minutes while `AI_ENABLED=false`), moves it to extracting, reads the PDF from MinIO, and reads each page with pdf.js: a page whose text layer has at least `LLM_TEXT_MIN_CHARS` (100) non-space characters goes as text, any other is rendered 1,000 px wide and sent as JPEG at quality 80. A document of text pages goes to the text model, any other to the primary with every page (text pages as text). The model answers to a JSON schema derived from the zod schema, at temperature 0; zod and the arithmetic checks (`checkArithmetic`: lines within 1 cent of the subtotal, or of the total less tax without one; subtotal plus tax equal to the total) validate it. Invalid output gets one repair call that lists the exact problems, then one fresh pass on the fallback model, then the invoice goes to needs_review with its extraction row (problems and output). A 429 on the first pass moves that pass to the fallback model (evals pass `fallbackOnRateLimit: false`). A scan with more page images than the fallback takes (3 for Groq's qwen) never goes to it: where the ladder would call the fallback, the invoice goes to needs_review with the problem `fallback_page_cap`. Every call is recorded in `llm_calls` as it ends, with the time it first waited on its role's bucket (`wait_ms`) apart from its own latency; the extraction row records the model, summed tokens, the step that succeeded and why the fallback ran. A 401, 403 or 404 (and Gemini's 400 `API_KEY_INVALID`) pauses the extract queue, logs `alert: "extract_paused"` and puts the job back without using an attempt; `pnpm extract:resume` restarts the queue once the setting is fixed and the worker restarted. A valid extraction saves one `extractions` row and the header fields in one transaction and queues `reconcile`; the carrier read is matched to the tenant's carriers by the domain's `matchCarrier`, the extraction keeps the rule in `carrier_match` (the reading itself stays in `result`), and no single match leaves the invoice without a carrier, which reconcile sends to needs_review (`no_shipment_match`). Rerunning it at any point writes nothing twice (status guards, unique `invoice_id`). A PDF holding several invoices is split by `first_page` into per-invoice PDFs and invoice rows (`parent_invoice_id`); a FlowProducer adds a `collect` parent with one child extract job per part (`ignoreDependencyOnFailure`), and the parent records each part's outcome in the upload's extraction row and marks it extracted. A reconcile job commits the move to reconciling on its own, then in one transaction locks the invoice row, matches the shipment by carrier and PRO number (locked too, so reconciles of one shipment run one at a time), loads the carrier's rate card versions (the domain picks the one in force on the ship date), its bands and accessorials, and the charge codes on other invoices already reconciled against the shipment, calls `reconcileInvoice`, writes the invoice lines (numbered by position, each with the version that priced it) and one discrepancy per finding (expected and billed cents, the explanation, the line and shipment), and sets reconciled with the shipment link. A carrier or PRO number that matches no shipment sets needs_review and writes nothing else; no version in force, a version without bands, minimum or fuel percentage, a shipment without miles, or a domain `RangeError` is permanent and dead-letters the job. A rerun or a second concurrent run waits on the invoice lock, finds the invoice reconciled and writes nothing. `tms-sync` runs every 5 minutes (one job scheduler), pages mock-tms from the saved cursor, upserts carriers and shipments (with miles) and saves the cursor in the same transaction per page, and retries a page in place on any transient failure (429, 5xx, timeouts, dropped connections) up to 10 times with the jittered backoff and a Retry-After floor; after that the attempt fails and the next resumes from the saved cursor. SIGTERM closes the workers after their running jobs.
- Error taxonomy (`packages/llm`): TransientError (timeouts, 408/425/5xx, dropped connections, found along the error's cause chain; carries Retry-After) is retried; its subclass RateLimitError (429, with Retry-After or Gemini's RetryInfo) also moves a first pass to the fallback model. PermanentError (unreadable or empty PDF, more than 20 pages, missing PDF, other provider 4xx) becomes BullMQ `UnrecoverableError`; its subclass ProviderConfigError (401, 403, 404, Gemini `API_KEY_INVALID`) pauses the extract queue instead. Error messages keep only the status and the provider's error code, never a response body (Groq's `json_validate_failed` echoes the model's output); validation messages name fields, never document values.
- Dead letters (`packages/pipeline`): one `failed` handler per worker; on a final failure it inserts a `dead_letters` row and marks the invoice failed, then copies the job to `<queue>-dlq`, all idempotent.     - A failure keeps only `error.type`.

    - Model tokens; paid-equivalent cost in micro-dollars (`paidCost`, priced even on free tiers); provider 429s.

## Known Limitations

- Measured on golden set v1 (2026-10-15), overcharge precision misses its target: 0.944 against 0.95, because a repeated scanned page read as two invoices gave two false duplicates.
- The eval's own end-to-end p95 (143 s, under its free-tier throttling with four cases in flight) and its free-tier ceiling (394 an hour) stay in its report. The README table takes those two rows from the k6 load test instead:
  - Low-load latency on the real models: max 4.7 s for n = 20.
  - System throughput at 3x the design rate on recorded replies: 6,000/h sustained, 0 lost.
- Free tiers cannot run real models at the design rate. The remit layout's title line was read as the carrier in 2 of 15 remit invoices, which then end needs_review. 90 cases give wide intervals.
- Invoices in any currency but USD end needs_review (`unsupported_currency`); rate cards have no currency and there is no FX yet.
- Rate card versions written before 0007 have no bands, minimum or fuel percentage, and shipments synced before it have no miles until the TMS sync reads them again (clear its cursor, see `docs/migrations.md`); reconciling against them dead-letters the job until the data is entered (then replay it).
- A reviewer corrects only the carrier and PRO number, and only of an invoice whose reading matched no shipment (user decision, 2026-10-16); an invoice whose extraction failed validation can be approved as billed or rejected, not corrected. A needs_review invoice's lines exist only in its extraction row, since lines are written once a version prices them.
- **Review UI:**
  - One reviewer, recorded as `reviewer`; a users table comes with a second reviewer.
  - The sign-in limit is counted in memory per server instance, so on Vercel each instance counts on its own (user decision); a hosted Redis such as Upstash makes it global.
  - Everyone using the UI shares the one API key's rate limits (`RATE_LIMIT_PER_MIN`): 60 requests and 10 uploads a minute per key, for all web traffic together (the demo's values live in `infra/`).
  - The invoice list's exact counts (`totalCount`, `offset`, `invoiceSummary`) and its search read every matching invoice of the tenant. That is fine at the demo's size; a trigram index on invoice number, PRO number and carrier name is the upgrade past about 100k invoices (`ponytail:` comments in `apps/api/src/graphql.ts`).
  - Invoices processed before migration 0013, and every seeded one, show only their Received entry in the audit trail.
  - Times are shown in UTC, since the server renders them.
  - Document marks need a digital PDF, and a value gets one only where it appears exactly once in the PDF's text: a total printed twice (the remit stub, a one-line invoice) or a boxed layout's repeated amounts get none, and EUR's `1.234,56` amounts are not matched.
  - Recent uploads are the latest invoices, shared by everyone signed in (one tenant, one reviewer).
  - The sidebar's counts are kept 10 s per server instance, so another Vercel instance can show counts up to 10 s old.
  - PNG and JPEG uploads ignore EXIF orientation, so a photo taken sideways stays sideways.
  - A repeated URL parameter errors the invoice lists, the public sample's included: production answered 500 for `/demo/invoices?q=a&q=b` and for `status` given twice (2026-10-18). Fixed in PR C1 (merged as `a2f046e`); production answers 200 since.
  - On the public demo no live invoice has a sample twin. `pnpm db:reset-demo` uploads the sample's PDFs anew, so their ids differ from the snapshot's. Offline, a live invoice page therefore lands on the sample list; a twin opens only from a sample id's URL.
  - Seeded invoices have no stored PDF, so their page says "No document is stored for this invoice." PR C2 (not merged) labels them as example data instead. That applies only when the api answers 404 to a HEAD for the document AND the trail holds only the synthetic Received entry. On the demo (2026-10-18) that is 500 of 513 invoices: MinIO holds 13 objects, one per upload. The 208 seeded approved invoices show no approval in their trail, since the seed writes no audit rows.
  - A finding's text is its stored evidence, which names the charge code in capitals ("INSIDE_DELIVERY is billed twice."). Fixed in PR C1 (merged as `a2f046e`): the web names the line as printed.
- Duplicates across invoices compare against invoices already reconciled for the shipment, so of two invoices billing one charge, the one reconciled second carries the finding, whichever arrived first.
- Possible duplicate invoices (branch `c2b-c3`, not merged): reconcile flags an invoice when another of its carrier, not rejected, has the same number. Two invoices both read before either reconciles each carry the finding. A reconciled invoice cannot be rejected (only needs_review moves to rejected), so after a reviewer confirms the duplicate the invoice can still be approved; the web's bulk buttons still show and get the api's refusal until C4.
- Upload invoices that were split stay extracted with no lines of their own.- One tenant per deployment (`TENANT_ID`); API keys do not carry a tenant yet, and job ids are content hashes without the tenant.
- Mistral is not used: its account answered every chat call with 429 (`x-ratelimit-limit-req-minute=0`, code 1300) with two keys, although it lists its models. The fallback is Groq's `qwen/qwen3.8-27b`, a preview model, on the text model's provider: one Groq outage leaves digital invoices without a model and scans without a fallback, and its 8,000 tokens a minute take about three one-page scans.
- Free-tier limits are small: Gemini publishes no free-tier table (about 500 requests a day for `gemini-3.5-flash-lite` and 20 for `gemini-3.8-flash` per unofficial sources, 2026-09); Groq allows 1,000 requests and 200,000 tokens a day and 8,000 tokens a minute per model. RPD limits are not tracked; a 429 falls back or retries.
- Gemini serves some retired model ids with a newer model (`gemini-3.7-flash` answered as `gemini-3.8-flash` on 2026-10-15), so `llm_calls.served_model` records what ran.
- Scans over 3 pages have no fallback: Groq's qwen takes at most 3 page images a request (and 4 would exceed its 8,000 tokens a minute), so such a scan that needs the fallback ends needs_review (`fallback_page_cap`). Batch and merge is the upgrade path if the 6b eval shows it matters. Gemini takes all 20 pages an upload may have in one request (about 0.3 MB of JPEG a page).
- The api accepts at most 4 MiB per file (step 9, under Vercel's 4.5 MB body cap), so a 20-page scan fits only below about 0.2 MB a page; the fixture generator's scans are about 0.7 MB a page (192 dpi), so a scan over 5 pages no longer fits.
- The eval smoke makes real model calls on every push to a same-repository PR (about 25K of Groq's 200K daily tokens a run), and the weekly full eval more; both share the free daily quotas with local runs, and a quota stop only warns.
- CI runs on GitHub (github.com/kwnhyk04/freightaudit): ci.yml on pull requests, release.yml and Dependabot have run green, with PRs #12 and #13 green (confirmed by the user on 2026-10-17), and PR #13's eval smoke posted its comment. Not yet seen on GitHub: nightly-eval.yml opening its issue on a broken floor.
- The api logs two false warnings at startup ("ContentTypeParser for 'application/pdf' not found", and the same for 'application/problem+json'): fastify-openapi-glue 4.11.5 checks response media types for a request parser too. They stay until it checks request bodies only (docs/todo.md).
- The demo backend changes only when someone runs `pnpm demo:up` on the PC (nothing deploys from CI), and it answers only while the PC is on and awake; otherwise the UI shows the sample.
- Documents are never cached: the web's document route and the api's answer `private, no-store` (PR #21, live 2026-10-18). Copies a browser kept under the earlier year-long header stay until that browser honours sign-out's `Clear-Site-Data: "cache"` or its site data is cleared.
- `pnpm audit` accepts two high advisories in dev-only contracts tooling (`auditConfig.ignoreGhsas` in `pnpm-workspace.yaml`, with reasons); Trivy fails only on criticals that have a fix (`--ignore-unfixed`). The api image has 4 fixable HIGH findings (brace-expansion among them), which the critical-only gate lets through.
- The worker's `/healthz` listens only after it reaches Redis (it schedules the TMS sync first), so its container is unhealthy while Redis is down.
- A split part whose bytes match an earlier upload reuses that invoice and job id; BullMQ then makes the old job a child of the split.
- `pnpm test:int` needs Docker and the Playwright Chromium (`pnpm --filter @freightaudit/evals exec playwright install --only-shell chromium`). `db:seed` refuses a database that already has data; `pnpm db:reset` empties and reseeds a local dev database.
- The Toxiproxy test reaches its fake TMS on the host as `host.docker.internal`. Docker Desktop forwards that to the host's loopback; on a Linux engine `host-gateway` is the bridge's gateway, so there the fake TMS listens on that address (`TOXIPROXY_UPSTREAM_HOST`, set by the Jest global setup), where every container on the default bridge can reach it while the test runs.
- A test run killed before its teardown leaves its containers running until the next `pnpm test:int` removes them.
- The migration runner records names only, so an edited applied migration goes unnoticed.
- `backfill-rate-card-versions.ts` only works between 0002 and 0004; after 0004 `rate_cards.carrier_id` no longer exists.
- Fixture bytes repeat only on the same machine and Chromium build; other fonts or browser versions render differently. Fixture invoices are single-page, and their ground truth holds only for a database seeded with `--scale=small`.
- oasdiff reports a new `InvoiceStatus` value as breaking (`response-property-enum-value-added`, ERR) against a base without it. `packages/contracts/oasdiff-ignore.txt` accepts step 9's `rejected` and the upload media type change, each under its reason; its lines go once main has them. Locally `contracts:breaking` needs a fetched base (`OASDIFF_BASE_REF=main` works); CI passes the base commit as `OASDIFF_BASE_REF` and skips the check on a branch's first push.
- 403 is documented but no key has restricted permissions. A request's 30 s `requestTimeout` covers receiving it, not the handler's work.
- Readiness proves TCP reachability only, not credentials; it switches to queries on the real clients when steps 3 and 4 add them.
- The web port is fixed at 3000 unless `--port` or `PORT` is passed. In development the web takes only its own keys from the root `.env`. Next.js's own logs are not JSON; the web's server lines are.
- mock-tms serves a fixed set of shipments; new ones never appear, so later syncs read one empty page. `infra/toxiproxy.json` proxies mock-tms on port 4010 regardless of `MOCK_TMS_PORT`.
- MinIO runs the community fork image `pgsty/minio` because upstream images were withdrawn.
- **Tracing:**
  - A batch upload is one trace holding every file's extract and reconcile. A 500-file batch would make a very large trace; per-file span links are the upgrade.
  - The fetch-based clients (MinIO, the TMS sync, the model providers) have no HTTP client spans; each model call has its GenAI span.
  - Web and mock-tms are not instrumented, and logs carry no trace ids.
  - instrumentation-pg puts Postgres' error message in a failed query's span status. Inputs are validated before they reach the database, so the message holds no document values, but a new path that writes unvalidated values could change that.
- **Exports:** without the observability profile, the OTLP exports fail quietly. Set `OTEL_SDK_DISABLED=true` to skip the SDK.
- **Load test:**
  - Part 1 measures the system on the recorded-fixture provider, not real models: a fixed 2,300 ms per call and no quotas, every upload a byte-variant of the two recorded fixtures.
  - Part 2's 20 invoices give p50, p90 and max, but no meaningful p95.
  - Neither part measures real models at the design rate; that needs paid tiers.
