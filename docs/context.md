## Overview and Objectives

AI-native portfolio project showing document extraction plus deterministic reconciliation for freight invoice audit (logistics / accounts payable domain).

## Scope and Requirements

- Upload single invoices or batches of up to 500 PDFs (digital and scanned).
- LLM extraction of header fields and line items, with validation, one repair attempt, and escalation to the fallback model.
- Deterministic reconciliation against versioned rate cards and shipments synced from a mock TMS.
- Review UI for discrepancies.
- Must demonstrate: backpressure, retries, pagination, partial failures, schema migrations.

Targets (design goals; measured on golden set v2 on 2026-10-27, see the README table and `evals/reports/2026-10-27-v2.md`; golden set v1's run of 2026-10-15 is `evals/reports/2026-10-15.md`):

| Metric | Target |
| --- | --- |
| Header field accuracy | 0.98 digital, 0.93 scanned |
| Line-item F1 | 0.95 digital, 0.88 scanned |
| Arithmetic consistency | 0.99 after repair |
| Overcharge precision / recall | 0.95 / 0.90 |
| Dollar recovery | 0.90 |
| False flag rate | 3% or lower |
| Escalation rate | 10% or lower |
| Extraction latency (3 pages or fewer) | p50 5 s, p95 12 s |
| End-to-end latency | p95 30 s |
| Throughput | 2,000 invoices/hour on 2 workers x concurrency 8 |
| Tokens per page (text path) | 4,000 input / 1,200 output |
| Cost per invoice | $0.02 digital, $0.05 scanned |

## Architecture and System Design

Workspaces exist as skeletons (step 1). Behavior below is planned unless listed under Implemented Functionality.

1. `apps/api`: Fastify REST + GraphQL. Stores PDFs in MinIO by content hash, writes invoice rows, enqueues `extract`. Returns 503 with Retry-After while more than `EXTRACT_HIGH_WATER` (5,000) extract jobs wait.
2. `apps/worker`: BullMQ queues `extract`, `reconcile`, `tms-sync`, each with a `<name>-dlq` dead-letter queue.
3. `apps/mock-tms`: fake TMS with cursor pagination, 10 req/s rate limit, fault injection.
4. `apps/web`: Next.js review UI, a backend for frontend: its server calls the api's GraphQL and REST with a server-only key; the browser never calls the api.
5. `packages/domain`: money, rate-card math, reconciliation. Pure functions.
6. `packages/llm` (provider layer, error taxonomy, PDF handling, AI limits), `packages/pipeline` (queues and job options, dead letters and replay, PDF object store; shared by api and worker), `packages/db`, `packages/contracts`, `packages/telemetry`, `evals/`.

Tooling: `packages/config` holds the shared tsconfig, ESLint and Jest presets plus the runtime env loader (`@freightaudit/config/env`). `packages/telemetry` holds the shared Fastify logging options and readiness checks, every metric instrument, and `./sdk`, which starts OpenTelemetry. Packages build to `dist/` with `tsc`; apps run TypeScript directly in dev through Node type stripping. Local infrastructure lives in `infra/docker-compose.yml`; `infra/docker-compose.prod.yml` turns it into the public demo's own project, `freightaudit-prod`.

## Invoice Lifecycle

One status set in Postgres (`invoice_status`), REST (`InvoiceStatus`, lowercase) and GraphQL (`InvoiceStatus`, uppercase): received, extracting, extracted, reconciling, reconciled, needs_review, approved, rejected, failed (user decisions, 2026-10-14; rejected 2026-10-16). An invoice starts as received when the api stores a new PDF. The table lists every allowed move; the `check_invoice_transition` trigger (migration 0006, replaced in 0007, 0013, 0015 and 0016) rejects any other update of `status`, whichever code writes it, and rejects approval, and since 0015 rejection, while any of the invoice's discrepancies is open. Repeating the current status is allowed. Since 0013 every status change is kept in `audit_events`: a trigger writes the pipeline's moves, and a reviewer action writes its own row (who, why, which fields) in the same transaction.

Findings do not change the status (user decision, 2026-10-14): an invoice with findings ends as reconciled, and each finding waits as an open discrepancy in the review queue (open discrepancies across invoices, GraphQL `discrepancies(status: OPEN)`). needs_review is reserved for extractions that could not be trusted: the extract job sets it when the model's output stays invalid after one repair and one pass on the fallback model, or when a scan with more page images than the fallback takes would need the fallback, and the reconcile job when the extracted carrier or PRO number matches no shipment.

| From | To | When |
| --- | --- | --- |
| received | extracting | The extract worker starts the job. |
| extracting | extracted | Extraction passes validation on the first pass, after one repair, or on the fallback model. |
| extracting | needs_review | The output stayed invalid after one repair and one pass on the fallback model (0009), or a scan with more page images than the fallback takes needed the fallback (problem `fallback_page_cap`); the extraction row keeps the problems and the output for a reviewer. |
| extracting | failed | Extraction used up its retries; the job moves to `dead_letters`, whose error the api shows as the invoice's `failure_reason`. |
| extracted | reconciling | The reconcile worker starts the job. |
| reconciling | reconciled | The shipment matched, and every line was checked against the rate card version in force on the ship date; each finding is saved as an open discrepancy. |
| reconciling | needs_review | The extracted carrier or PRO number matches no shipment, so the extraction cannot be trusted. |
| reconciling | failed | Reconciliation used up its retries or met data it cannot price (no version in force, a version without linehaul terms, a shipment without miles); the job moves to `dead_letters`, and the worker's dead-letter handler marks the invoice failed with that error as its `failure_reason`. |
| reconciled | approved | `approveInvoice`, once every discrepancy is confirmed or dismissed (the trigger enforces it), and none is a confirmed possible duplicate (the api refuses it, since C4a, `e9ef0ba`). |
| reconciled | rejected | `rejectInvoice` with a reason of 1 to 1,000 characters; its open discrepancies close with it, each with a `discrepancy_closed` audit row (0015, C4a, `e9ef0ba`). |
| needs_review | approved | `approveInvoice`, once a reviewer has checked the document, unless another invoice of its carrier has its number (the next row). |
| needs_review | reconciled | `approveInvoice` ("Approve as billed") on an invoice whose reading saved a carrier and a number, when another invoice of that carrier, not rejected, has the same number (reconcile's lookup, `possibleDuplicate` in `packages/db`). It is not approved: it waits with an open `duplicate_invoice` finding and no shipment, lines or rate card version, so it was never checked against the rate card, and the answer's status and hold say so (0016, #34, `6b3f24b`). |
| needs_review | extracted | `correctInvoice`: a reviewer corrects the carrier or PRO number of an invoice whose reading matched no shipment (`no_shipment_match`); the reconcile job is queued again and matches with the corrected values (0013). |
| needs_review | rejected | `rejectInvoice` with a reason of 1 to 1,000 characters (0013). |
| failed | received | Replay of an `extract` dead letter; it closes the dead letter, which clears `failure_reason`. |
| failed | extracted | Replay of a `reconcile` dead letter, once the data is fixed; the job then reconciles the invoice. |

`approved` and `rejected` are final. A retried job keeps the current status, because jobs are idempotent (job id = content hash). Never sort by status: Postgres orders the enum `received, extracting, extracted, reconciling, needs_review, reconciled, approved, rejected, failed`, since values added later cannot move existing ones.

- Seed (`pnpm db:seed --scale=small|large`): deterministic (`faker.seed(42)`) data for an empty, migrated database, in one transaction; two small seeds give identical rows. Small is 1 tenant, 6 fictional carriers, 5,000 shipments and 500 invoices (1,268 lines, 454 extractions, 111 discrepancies of which 79 open, about 1 s); large is 50,000 shipments and 20,000 invoices (51,065 lines, 18,232 extractions, 4,842 discrepancies, about 17 s). Each carrier gets two rate card versions, with a rate increase on 2026-01-01: three graduated per-mile bands (from miles 0, 250 and 1,000), a minimum, a fuel percentage and four accessorials; shipments get 25 to 2,500 miles. Lines bill what the version in force on the ship date contracts (linehaul and fuel through `rateShipment`), plus one planted overcharge (rate mismatch, uncontracted or duplicate charge) on half of the extracted, reconciling and reconciled invoices and 15 % of the approved ones. Invoices cover all 8 statuses and follow the lifecycle: every invoice past extraction has an `extractions` row in the model's output shape; reconciled and approved ones have lines and a shipment, with their findings open on reconciled invoices and decided on approved ones; extracted and reconciling ones wait for the reconcile job, so their planted overcharges exist only in the ground truth; needs_review ones carry a PRO number with its last digit misread, which matches no shipment. `seed()` returns its ground truth (`buildSeed` builds it in memory): for each invoice a reconciler can check, every line's contracted and billed cents and every planted overcharge with its expected cents, billed cents and explanation.
- Reset (`pnpm db:reset`, dev only, `packages/pipeline/scripts/reset.ts`): obliterates this deployment's BullMQ queues and dead-letter queues with BullMQ's `obliterate` (jobs and their ids, so a PDF uploaded before the reset is extracted again), refusing while a job runs and unless Redis is on localhost or 127.0.0.1; then, through `packages/db/scripts/reset.ts`, it drops schema `public` (every app table, type, function and its data) and recreates it as a new database has it, migrates from empty and seeds `--scale=small` (about 3 s).   - The two approve decisions then approve the invoice, with reason `as billed` or `at rate card`. DISPUTE leaves it reconciled and writes only the findings' rows.
  - It refuses with CONFLICT ("This invoice changed since you opened it…") when the invoice's findings differ from the ids and versions the reviewer saw. A version is the finding's `updated_at` to the microsecond.

- Worker (`apps/worker`): `extract` (`EXTRACT_CONCURRENCY`, 1 to 8, default 8; the demo's compose file sets 1), `reconcile` (8) and `tms-sync` (1) workers share one Redis connection, a 60 s lock (`JOB_LOCK_MS`), stalled checks every half lock, `maxStalledCount` 1 and the `jittered` backoff (exponential from 2 s, capped at 60 s, full jitter, never below an error's Retry-After); jobs have 5 attempts. An extract job loads the invoice, delays itself with `moveToDelayed` until the next UTC midnight once the day's token budget is spent (5 minutes while `AI_ENABLED=false`), moves it to extracting, reads the PDF from MinIO, and reads each page with pdf.js: a page whose text layer has at least `LLM_TEXT_MIN_CHARS` (100) non-space characters goes as text, any other is rendered 1,000 px wide and sent as JPEG at quality 80. A document of text pages goes to the text model, any other to the primary with every page (text pages as text). The model answers to a JSON schema derived from the zod schema, at temperature 0; zod and the arithmetic checks (`checkArithmetic`: lines within 1 cent of the subtotal, or of the total less tax without one; subtotal plus tax equal to the total) validate it. Invalid output gets one repair call that lists the exact problems, then one fresh pass on the fallback model, then the invoice goes to needs_review with its extraction row (problems and output). A 429 on the first pass moves that pass to the fallback model (evals pass `fallbackOnRateLimit: false`). A scan with more page images than the fallback takes (3 for Groq's qwen) never goes to it: where the ladder would call the fallback, the invoice goes to needs_review with the problem `fallback_page_cap`. Every call is recorded in `llm_calls` as it ends, with the time it first waited on its role's bucket (`wait_ms`) apart from its own latency; the extraction row records the model, summed tokens, the step that succeeded and why the fallback ran. A 401, 403 or 404 (and Gemini's 400 `API_KEY_INVALID`) pauses the extract queue, logs `alert: "extract_paused"` and puts the job back without using an attempt; `pnpm extract:resume` restarts the queue once the setting is fixed and the worker restarted. A valid extraction saves one `extractions` row and the header fields in one transaction and queues `reconcile`; the carrier read is matched to the tenant's carriers by the domain's `matchCarrier`, the extraction keeps the rule in `carrier_match` (the reading itself stays in `result`), and no single match leaves the invoice without a carrier, which reconcile sends to needs_review (`no_shipment_match`). Rerunning it at any point writes nothing twice (status guards, unique `invoice_id`). A PDF holding several invoices is split by `first_page` into per-invoice PDFs and invoice rows (`parent_invoice_id`); a FlowProducer adds a `collect` parent with one child extract job per part (`ignoreDependencyOnFailure`), and the parent records each part's outcome in the upload's extraction row and marks it extracted. A reconcile job commits the move to reconciling on its own, then in one transaction locks the invoice row, matches the shipment by carrier and PRO number (locked too, so reconciles of one shipment run one at a time), loads the carrier's rate card versions (the domain picks the one in force on the ship date), its bands and accessorials, and the charge codes on other invoices already reconciled against the shipment, calls `reconcileInvoice`, writes the invoice lines (numbered by position, each with the version that priced it) and one discrepancy per finding (expected and billed cents, the explanation, the line and shipment, and a possible duplicate from `possibleDuplicate` in `packages/db`, the lookup the api's approval from review shares), and sets reconciled with the shipment link. A carrier or PRO number that matches no shipment sets needs_review and writes nothing else; no version in force, a version without bands, minimum or fuel percentage, a shipment without miles, or a domain `RangeError` is permanent and dead-letters the job. A rerun or a second concurrent run waits on the invoice lock, finds the invoice reconciled and writes nothing. `tms-sync` runs every 5 minutes (one job scheduler), pages mock-tms from the saved cursor, upserts carriers and shipments (with miles) and saves the cursor in the same transaction per page, and retries a page in place on any transient failure (429, 5xx, timeouts, dropped connections) up to 10 times with the jittered backoff and a Retry-After floor; after that the attempt fails and the next resumes from the saved cursor. SIGTERM closes the workers after their running jobs.
- Error taxonomy (`packages/llm`): TransientError (timeouts, 408/425/5xx, dropped connections, found along the error's cause chain; carries Retry-After) is retried; its subclass RateLimitError (429, with Retry-After or Gemini's RetryInfo) also moves a first pass to the fallback model. PermanentError (unreadable or empty PDF, more than 20 pages, missing PDF, other provider 4xx) becomes BullMQ `UnrecoverableError`; its subclass ProviderConfigError (401, 403, 404, Gemini `API_KEY_INVALID`) pauses the extract queue instead. - **Telemetry** (step 8): the api and worker start OpenTelemetry through `node --import ./src/telemetry.ts`, which calls `startTelemetry` from `@freightaudit/telemetry/sdk`. `OTEL_SDK_DISABLED` turns it off; it exports to `OTEL_EXPORTER_OTLP_ENDPOINT` every `OTEL_METRIC_EXPORT_INTERVAL` ms.
  - **SDK and hooks:** NodeSDK, with OTLP/JSON to the collector of the observability profile. The import-in-the-middle ESM hook is limited to the hooked modules.
  - **Instrumentations:**
    - http ignores the probes; its metric is `http.server.request.duration` in seconds.
    - @fastify/otel sets `http.route` and records no exceptions.
    - pg records SQL with `$n` placeholders, inside a job or request only.
    - ioredis records command names only.
    - `service.instance.id` is hostname-pid.
  - **Trace context across BullMQ** (`packages/pipeline/src/tracing.ts`):
    - `send()` adds jobs inside a `send <queue>` PRODUCER span and stores its `traceparent` and `tracestate` as `data.otel`.
    - `consume()` runs every attempt as a `process <queue>` CONSUMER span under it, with the job name, attempt and invoice id.
    - A split's flow is one `send extract` span whose context the collect parent and every part carry.
    - A replay continues the replay request's trace.
    - A failure keeps only `error.type`.
    - One upload is therefore one trace: request, extract, each model call, reconcile.
  - **Model calls** are CLIENT spans named `generate_content <model>` (Gemini) or `chat <model>`. They use the GenAI semantic conventions as of semconv v1.41.1 (development, inlined): provider name, request and response model, input and output tokens, finish reasons, temperature, output type json, plus `freightaudit.llm.role` and `step`. They never record the prompt, the pages or the output.
  - **Metrics** (`packages/telemetry/src/metrics.ts`):
    - Queue gauges, read from Redis at each export by the worker: jobs per queue and state, dead letters waiting per `<queue>-dlq`, and `extract.paused`, which is the circuit breaker.
    - Job duration and wait histograms; retries by error class.
    - Model tokens; paid-equivalent cost in micro-dollars (`paidCost`, priced even on free tiers); provider 429s.
    - Extraction escalations by final step and fallbacks by reason; needs_review by reason code; intake 503s.
  - **Dashboard:** Grafana provisions `infra/grafana/freightaudit.json`, uid `freightaudit`.
  - **Alerts:** Prometheus loads `infra/prometheus-alerts.yml`, which a promtool test covers and CI's lint job runs:
    - dead letters waiting over 10 minutes
    - extract wait p95 over 60 s for 5 minutes
    - paid-equivalent cost per invoice over $0.05 in the last hour
    - circuit breaker open
- **Rate limits:** the per-key limits are `RATE_LIMIT_PER_MIN` (60) and `UPLOAD_RATE_LIMIT_PER_MIN` (10).
- **Load test** (`loadtest/k6.js`): run as the compose `k6` service (profile `loadtest`). It writes `loadtest/<scenario>-results.json`, whose numbers the README eval table shows through `loadTestRows` in `evals/harness/report.ts`.
  - **Part 1** (`SCENARIO=system`):
    - Load: 2 minutes at the normal 2,000/h, then 10 minutes at 6,000/h.

  - Low-load latency on the real models: max 4.7 s for n = 20.
  - System throughput at 3x the design rate on recorded replies: 6,000/h sustained, 0 lost.
- Free tiers cannot run real models at the design rate. A document title beside the carrier's name was read as part of it on 2 digital invoices of golden set v2's test split (g2-036, g2-043; on v1, 2 of 15 remit invoices). The carrier is matched in code, so they reconcile, while header accuracy counts the misread. 98 cases give wide intervals, and the ci subset's floors, from 20 cases, catch only large regressions.
- Invoices in any currency but USD end needs_review (`unsupported_currency`); rate cards have no currency and there is no FX yet.
- Rate card versions written before 0007 have no bands, minimum or fuel percentage, and shipments synced before it have no miles until the TMS sync reads them again (clear its cursor, see `docs/migrations.md`); reconciling against them dead-letters the job until the data is entered (then replay it).

- A test run killed before its teardown leaves its containers running until the next `pnpm test:int` removes them.
- The migration runner records names only, so an edited applied migration goes unnoticed.
- `backfill-rate-card-versions.ts` only works between 0002 and 0004; after 0004 `rate_cards.carrier_id` no longer exists.
- Fixture bytes repeat only on the same machine and Chromium build; other fonts or browser versions render differently. Fixture invoices are single-page, and their ground truth holds only for a database seeded with `--scale=small`.
- oasdiff reports a new `InvoiceStatus` value as breaking (`response-property-enum-value-added`, ERR) against a base without it. `packages/contracts/oasdiff-ignore.txt` accepts such a change, under its reason, until main has it. Its last lines (step 9's `rejected` and the upload media type change, C3's `duplicate_invoice` and C4a's finding status `closed`) were deleted in `9d0a2d6` (#33), since main has had every one since `e9ef0ba` (#28); `contracts:breaking` still passes. Locally `contracts:breaking` needs a fetched base (`OASDIFF_BASE_REF=main` works); CI passes the base commit as `OASDIFF_BASE_REF` and skips the check on a branch's first push.
- 403 is documented but no key has restricted permissions. A request's 30 s `requestTimeout` covers receiving it, not the handler's work.
- Readiness proves TCP reachability only, not credentials; it switches to queries on the real clients when steps 3 and 4 add them.
- The web port is fixed at 3000 unless `--port` or `PORT` is passed. In development the web takes only its own keys from the root `.env`. Next.js's own logs are not JSON; the web's server lines are.
- mock-tms serves a fixed set of shipments; new ones never appear, so later syncs read one empty page. `infra/toxiproxy.json` proxies mock-tms on port 4010 regardless of `MOCK_TMS_PORT`.
- MinIO runs the community fork image `pgsty/minio` because upstream images were withdrawn.
- **Tracing:**
  - A batch upload is one trace holding every file's extract and reconcile. A 500-file batch would make a very large trace; per-file span links are the upgrade.
  - The fetch-based clients (MinIO, the TMS sync, the model providers) have no HTTP client spans; each model call has its GenAI span.
  - Web and mock-tms are not instrumented, and logs carry no trace ids.
  - instrumentation-pg puts Postgres' error message in a failed query's span status. Inputs are validated before they reach the database, so the message holds no document values, but a new path that writes unvalidated values could change that.
- **Exports:** without the observability profile, the OTLP exports fail quietly. Set `OTEL_SDK_DISABLED=true` to skip the SDK.
- **Load test:**
  - Part 1 measures the system on the recorded-fixture provider, not real models: a fixed 2,300 ms per call and no quotas, every upload a byte-variant of the two recorded fixtures.
  - Part 2's 20 invoices give p50, p90 and max, but no meaningful p95.
  - Neither part measures real models at the design rate; that needs paid tiers.
